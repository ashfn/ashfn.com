I wanted to make a Tor version of this site. Running an onion service myself seemed like a good way to understand how it worked.

An onion service is reached entirely through the Tor network. The connection is encrypted between the visitor and the service, and the protocol lets a service accept connections without publishing its server’s IP address. The [Tor Project’s explanation](https://community.torproject.org/onion-services/overview/) goes through how the two sides find each other.

Before I got very far with the hosting, though, I got distracted by the address.

## Why a vanity address?

A normal Tor v3 address is a string of 56 base32 characters followed by `.onion`. Unlike a regular domain, it comes from a cryptographic public key. You cannot just register `ashfncom.onion` and point it at a server.

I wanted something I could recognise in a list of otherwise random-looking addresses. A prefix like `ashfncom` makes the connection to this site obvious at a glance, and makes the address easier to distinguish when sharing or bookmarking it. It does not shorten the rest of the address, and checking a familiar prefix is not the same as verifying the full hostname, but it is a useful visual cue.

To get that prefix, you have to search: generate candidates, check their public keys, and keep a key whose address begins with the letters you want. Longer prefixes quickly turn that search into a substantial computation. That was the part that caught my attention.

## Why try a GPU?

There were already tools for this. [cathugger’s mkp224o](https://github.com/cathugger/mkp224o) could generate the address I wanted, and simply running it on the CPU would have been a perfectly reasonable way to finish the hosting project.

But I had an RTX 3070, and I wanted to see whether I could make the search faster by using it. Cryptocurrency mining was the example I had in mind: [early GPU miners](https://raw.githubusercontent.com/ckolivas/cgminer/v3.7.2/README) had shown how effective lots of parallel workers could be at repetitive cryptographic calculations. That made a search with many independent candidates seem like a promising GPU workload.

Mining’s hash calculations are different from the elliptic-curve arithmetic here, so I still needed to find out how well this particular search would run on a GPU. I decided to build a CUDA version and benchmark it against mkp224o.

## Starting with the CPU

For the CPU baseline, I ran mkp224o on a Ryzen 7 2700X with eight cores and sixteen hardware threads. The same machine had the RTX 3070 with 8 GiB of VRAM. The GPU stayed at its default 220 W power cap; I did not change its clocks, power limit or fan settings.

I tried several mkp224o arithmetic backends and thread counts. The fastest configuration used `amd64-64-24k`, sixteen threads, integer filtering and upstream batch mode, compiled with `-O3 -march=native -fomit-frame-pointer`.

Three separate 30-second CPU runs gave a median of **42.029 million candidates/sec**, with results between 42.004 and 42.273 million. I used the long filter `zzzzzzzzzzzz` so successful key exports would not keep interrupting the benchmark. The last cumulative CPU samples were at about 29.1 seconds, because shutdown did not emit another sample.

## Building it with Astra

I had never written CUDA kernels before, so I used OpenAI’s new [GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra) to help write and iterate on them. It also helped with the Python/CuPy runner and the checks needed to compare successive versions.

Python handled initialization, compilation, launches and saving matches, while the CUDA kernels did the expensive arithmetic on the GPU. CuPy compiled those kernels through NVRTC, so the setup did not need a system installation of `nvcc`.

The arithmetic itself came from an existing implementation: the source generator adapts ref10 from the [pinned mkp224o source](https://github.com/cathugger/mkp224o/tree/5172c0fd71740ca0b11da8149a2575dcf331d7ab) into CUDA device functions. The main job was arranging that arithmetic into an efficient search.

## What is a candidate?

A Tor v3 hostname encodes a 32-byte Ed25519 public key, a two-byte checksum and a version byte into 56 base32 characters. For a short vanity prefix, the search can check the relevant public-key bits directly.

Each GPU lane starts from its own OS-random seed. The CPU expands and clamps the secret and initializes the public points. If the initial secret scalar is $a_0$ and the Ed25519 base point is $B$, the lane walks through:

$$
a_i = a_0 + 8i,
\qquad P_i = a_i B.
$$

That means the next public point is simply:

$$
P_{i+1} = P_i + 8B.
$$

Adding a fixed point is much cheaper than doing a complete scalar multiplication for every candidate. Secret material stays on the CPU; the GPU receives public points. When it reports a hit, the CPU reconstructs the full public key independently with libsodium, verifies it and generates the complete onion hostname.

Throughout this post, throughput means **candidate public-key prefix checks**.

## Montgomery’s trick

One expensive part of checking a candidate is converting projective coordinates back into an affine coordinate. In the original Edwards kernel, recovering $y$ involves:

$$
\begin{aligned}
y &= Y/Z = YZ^{-1} \pmod p,\\
p &= 2^{255}-19.
\end{aligned}
$$

A field inversion is much more expensive than a multiplication. Doing one inversion for every candidate wastes a lot of work.

**Montgomery’s trick** computes the inverses of a whole batch using just one inversion. Suppose the batch has nonzero denominators $z_1,\ldots,z_n$ in $\mathbb{F}_p$. First calculate their prefix products:

$$
P_0=1,
\qquad P_i=\prod_{j=1}^{i}z_j.
$$

Then invert only the final product:

$$
r=P_n^{-1}.
$$

Work backwards through the batch. At each step:

$$
\begin{aligned}
z_i^{-1} &= rP_{i-1},\\
r &\leftarrow rz_i.
\end{aligned}
$$

Why does this work? Before processing index $i$, we have $r=P_i^{-1}$. Since $P_i=P_{i-1}z_i$:

$$
P_i^{-1}P_{i-1}=z_i^{-1}.
$$

Multiplying the running inverse by $z_i$ then leaves $P_{i-1}^{-1}$, ready for the next step.

For three denominators, it looks like this:

$$
\begin{aligned}
r &= (z_1z_2z_3)^{-1},\\
z_3^{-1} &= r(z_1z_2),\\
r &\leftarrow rz_3=(z_1z_2)^{-1},\\
z_2^{-1} &= rz_1,\\
r &\leftarrow rz_2=z_1^{-1}.
\end{aligned}
$$

Ignoring multiplications by one at the boundaries, the basic batch-inversion algorithm replaces $n$ inversions with **one inversion and $3(n-1)$ multiplications**. Recovering coordinates adds its own multiplications. The nonzero-denominator assumption matters: zero has no field inverse.

On the GPU, each lane batches its own candidates. Larger batches spread that one expensive inversion across more work, but need more scratch memory. Finding a good batch size was a large part of the tuning.

## Crossing a billion

The first sustained CUDA configuration used 32,768 lanes, 128 candidates per lane per batch, and 64 threads per block. It needed 0.625 GiB of scratch storage and reached a three-trial median of **896.748 million candidates/sec**.

I then specialized compilation for the prefix length and diagnostic mode. The actual prefix letters stayed runtime inputs, but the compiler could remove irrelevant branches, unused encoded bytes and sign handling that short prefixes did not need. Compiler-reported register use fell from 242 to 180 registers per thread, with no local spill storage in those two compared variants.

Increasing the batch to 256 and using 32 threads per block pushed the median to **1.010 billion/sec**. All three 30-second trials exceeded a billion, although throughput declined as the card warmed. Scratch storage increased to 1.25 GiB.

## A cheaper curve walk

The next improvement came from studying [ActiveTK’s GPUonion](https://github.com/ActiveTK/GPUonion), particularly its [optimization notes](https://github.com/ActiveTK/GPUonion/blob/a87d38a7c74c20ed76c75196ab6531b244a73c20/Optimize.md). The useful idea was a different coordinate representation and **differential addition**. This also carries Montgomery’s name, but is separate from the batch-inversion trick above. I applied the technique to the existing ref10 implementation; no GPUonion source files were copied or vendored.

The Edwards $y$ coordinate and Montgomery coordinate $u$ are related by:

$$
u=\frac{1+y}{1-y},
\qquad y=\frac{u-1}{u+1}.
$$

Writing $u=U/W$ gives a convenient projective form:

$$
y=\frac{U-W}{U+W}.
$$

These coordinate relationships are also described in [RFC 7748](https://www.rfc-editor.org/rfc/rfc7748.html). The kernel keeps the current and previous points, whose difference is the fixed step $8B$. Let:

$$
\begin{aligned}
N &= U-W,\qquad D=U+W,\\
\kappa &= y(8B).
\end{aligned}
$$

The next projective point can then be computed as:

$$
\begin{aligned}
U_{\mathrm{next}} &= W_{\mathrm{prev}}(N+\kappa D)^2,\\
W_{\mathrm{next}} &= U_{\mathrm{prev}}(N-\kappa D)^2.
\end{aligned}
$$

This is the recurrence used in my kernel: three field multiplications and two squarings per step, compared with seven multiplications in the previous Edwards mixed addition. Because the step is fixed, $\kappa$ can be compiled into the kernel as a constant.

### Combining it with batch inversion

We still need to recover each candidate’s Edwards $y_i=N_i/D_i$ to check its prefix. Here the same batch-inversion idea also saves memory.

Let $Q_{i-1}$ be the product of the preceding denominators. During the forward pass, store a *weighted numerator*:

$$
\begin{aligned}
Q_0 &= 1,\\
Q_i &= Q_{i-1}D_i,\\
A_i &= N_iQ_{i-1}.
\end{aligned}
$$

Invert the final product once, then walk backwards. When the running inverse is $r=Q_i^{-1}$:

$$
\begin{aligned}
y_i &= A_i r\\
    &= N_iQ_{i-1}Q_i^{-1}\\
    &= N_iD_i^{-1},\\
r &\leftarrow rD_i.
\end{aligned}
$$

Now the scratch buffer only needs **$A_i$ and $D_i$**. There is no separate array for every prefix product. Normal scratch reads and writes dropped from 240 to 160 bytes per candidate. That allowed a batch of 512 in the same 1.25 GiB allocation.

The final configuration was **32,768 lanes × 512 candidates, with 32 threads per block**: 16,777,216 candidates per launch.

There is a limitation: the Montgomery-only state loses the Edwards $x$ sign. The automatic backend uses this path for prefix lengths 1–49, falling back to the Edwards kernel for lengths 50–51.

## The benchmark results

| Stage | Median candidates/sec | Relative to CPU |
|---|---:|---:|
| Tuned CPU, 16 threads | 42.029 million | 1× |
| Initial sustained CUDA | 896.748 million | 21.34× |
| Specialized Edwards CUDA | 1.010 billion | 24.02× |
| Montgomery CUDA | **1.338 billion** | **31.83×** |

The final three GPU trials measured **1.347, 1.338 and 1.330 billion/sec**, each over about 30 seconds. That is a 32.50% improvement over the specialized Edwards median.

These GPU timings include launches, synchronization, result-counter reads and hit-index transfers. They exclude initial seed generation, context setup, JIT compilation, warm-up and writing key files. Short tuning sweeps helped choose settings, but the headline figures come from the repeated trials.

During a longer search, a recorded window of about 27 minutes averaged **1.311 billion candidates/sec**, including initialization and pauses to save matches and reseed. That average comes from total completed candidates divided by total measured time. The full campaign checked **2,615,299,538,944 candidates**.

## The lucky part

The campaign retained four `ashfncom` addresses. One of them was much nicer than I had expected:

<p className="break-all">ashfncomabccvkuuvzbsjobu5wvtlw2wpz4mj3co5g5boyturbf36cyd.onion</p>

This is the address generated by the experiment. The onion site is not hosted yet.

I had only asked for `ashfncom`; the extra `abc` appeared by chance.

| Found on 14 September, UTC | Address beginning |
|---|---|
| 08:17:33.685473 | `ashfncomfeay…` |
| **08:36:08.983447** | **`ashfncomabc…`** |
| 08:36:11.810204 | `ashfncomkvt4…` |
| 08:43:31.083073 | `ashfncomtbcj…` |

The second and third matches were only **2.827 seconds apart**, after a much longer preceding gap. Random searches do not produce evenly spaced successes.

Under the usual uniform-prefix model, an eight-character base32 target has probability:

$$
\Pr(\text{match})=32^{-8}.
$$

At the final benchmark median, the expected waiting time is:

$$
\mathbb E[T]=\frac{32^8}{R}
\approx 13.70\text{ minutes}.
$$

Every extra specified character multiplies the expected work by 32. Deliberately searching for all eleven characters of `ashfncomabc` would take **about 312 days on average** at the same uninterrupted rate:

$$
\mathbb E[T_{11}]=\frac{32^{11}}{R}.
$$

Given an `ashfncom` match, a particular three-character extension such as `abc` has probability $32^{-3}$, or **one in 32,768**. Across four matches, the probability of at least one *pre-specified* `abc` extension is:

$$
1-(1-32^{-3})^4\approx 0.0122\%.
$$

But I noticed the nice extension after seeing the results. Other memorable endings might also have made me happy. This was an eight-character search that got lucky, not evidence that an intentional eleven-character search normally takes minutes.

## Checking and keeping the keys

Speed is only useful if a saved key controls the hostname it claims to. The checks compared GPU results with libsodium, exercised long walks and scalar carries, tested prefix masks and batch boundaries, and verified Tor’s file formats and hostname checksums. The Montgomery suite covered 104,007 candidate checks, including 69,338 serialized $y$-coordinate comparisons. Those are test counts, not a claim of that many independent secret keys or a cryptographic audit.

The continuous runner validated each match before saving it, wrote through a temporary directory, flushed the files and atomically moved the finished result into place. Key files had mode `0600`, and directories `0700`. There were no incomplete exports.

It also exported at most one match from a walker’s lifetime, then initialized all lanes again with fresh randomness. Keeping multiple keys from related scalar walks would expose a known relationship between their secrets. The reseeding cost is included in the longer-run average above.

## Hosting can wait

Finding the address was only one part of the project. I tested a small Docker setup locally, but the onion service is not ready to host publicly. I have kept that work for later; this site is currently served as static files on GitHub Pages.

## Making it work without JavaScript

I also wanted the site to remain readable and usable with scripts turned off, including for a future onion version. Tor Browser’s [Safest setting](https://support.torproject.org/tor-browser/features/security-levels/) disables JavaScript by default and restricts some fonts, icons and images, so testing with JavaScript disabled alone was not enough.

I kept the layout from the old Next.js site but moved the rendering to build time. Articles, syntax highlighting and these equations arrive as ready-made HTML and CSS. The browser does not need React to display them.

For the controls, I used what the browser already provides. The contents list uses anchor links, expandable JSON uses `details` and `summary`, and the theme button is a checkbox whose state changes the colours through CSS. Code can be opened as plain text for manual copying. Small optional scripts add conveniences such as remembering the theme, copying to the clipboard and following the current heading while scrolling; the Easter eggs also need JavaScript.

The icons caught me out: some SVGs disappeared in the stricter browser settings, leaving empty buttons and link boxes. I replaced the small UI icons with a single PNG sprite, using CSS masks to colour them for either theme. I then checked the pages in Firefox with JavaScript, SVG rendering and downloadable fonts disabled, at desktop and mobile sizes.

I set out to put this site on Tor and ended up spending most of the time on its address. The unexpected `abc` made that detour especially satisfying, and the work left me with a small site that works with scripts turned off. Hosting the onion version can come later.
